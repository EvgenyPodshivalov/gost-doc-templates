# Шаблоны документации по ГОСТ

Репозиторий для разработчиков и аналитиков, которым нужно сдать документацию по ГОСТ, а опыта работы с комплексом 34 нет. Внутри лежат шаблоны в Markdown, предзаполненные пояснениями: что писать в каждом разделе, откуда брать значение и на чём обычно спотыкаются.

Логика везде одна: вендор поставляет систему, заказчик принимает её по техническому заданию. Такие документы читают несколько сторон сразу, включая службу информационной безопасности, поэтому цена ошибки в них выше, чем в обычной внутренней документации.

Первым сделан ПМИ. Остальное по мере надобности, см. раздел «Что дальше».

## Быстрый старт

```bash
git clone <url-репозитория>
cd gost-doc-templates

# 1. Определиться со стандартом: АС или программное средство
#    docs/standards-choice.md

# 2. Скопировать шаблон под рабочим именем.
#    Каталог work/ не отслеживается git, рабочие документы туда и кладут
mkdir -p work
cp templates/pmi/pmi-gost-r-59795.md work/PMI-mysystem-v0.1.md

# 3. Заполнить. Найти незакрытые места:
grep -o '{{[^}]*}}' work/PMI-mysystem-v0.1.md | sort -u

# 4. Пройти чек-лист: templates/pmi/release-checklist.md

# 5. Вырезать пояснения и собрать чистовик
grep -v '^>' work/PMI-mysystem-v0.1.md > work/PMI-mysystem-v1.0-clean.md
pandoc work/PMI-mysystem-v1.0-clean.md -o PMI-mysystem-v1.0.docx \
  --reference-doc=шаблон-организации.docx
```

## На чём основаны шаблоны

ПМИ на автоматизированную систему собран по ГОСТ Р 59795-2021 (раздел 5.13 задаёт восемь разделов документа) и ГОСТ Р 59792-2021 (виды испытаний, обязательный перечень проверок, структура протокола). Код документа и правила обозначения по ГОСТ 34.201-2020.

Вариант для программного средства собран по ГОСТ 19.301-79, это ЕСПД.

Отдельно стоит запомнить две вещи. ГОСТ 34.603-92 утратил силу в России 30 апреля 2022 года, вместо него действует ГОСТ Р 59792-2021. РД 50-34.698-90 отменён, требования к содержанию документов перешли в ГОСТ Р 59795-2021. Шаблоны, которые ходят по чатам и ссылаются на эти два документа, устарели. Таблица со статусами и ссылками: [docs/standards-status.md](docs/standards-status.md).

## Как устроены пояснения

В шаблонах два вида вставок.

В `{{ЗАГЛУШКА}}` подставляется значение. Все незакрытые находятся грепом, перед сдачей их быть не должно.

Строка, начинающаяся с `>` — пояснение для того, кто пишет документ. В чистовик оно не идёт и вырезается одной командой. Пояснение отвечает на три вопроса: что сюда пишут, откуда берут значение, что здесь обычно ломается.

Пример из раздела про ограничения:

> Ограничения формулируются как ограничения документа, а не как решения сторон. Правильно: «Проверка отказоустойчивости в объём настоящих испытаний не входит, требование проверяется на этапе таком-то». Неправильно: «Заказчик отказался от проверки отказоустойчивости».

## Дисциплина, ради которой всё это

Три правила, которые экономят циклы доработки больше, чем любые шаблоны.

Каждая проверка ссылается на пункт ТЗ, и ссылка проверена по живому ТЗ. Не «должна совпадать», а вы открыли пункт и прочитали.

Перед ответом рецензенту «учтено в п. X» пункт X открывается. В одном разборе из 53 ответов 24 разошлись с документом именно потому, что этого не делали.

После массовой замены по документу идёт отдельный проход на регресс. Один прогон замены однажды породил восемь новых дефектов: висящие ссылки, устаревшие диапазоны, группа с прежним названием.
