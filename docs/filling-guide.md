# Как работать с шаблоном

Шаблоны лежат в Markdown, потому что в этом формате видно историю правок и можно грепать. Готовый документ почти всегда уходит в .docx или .pdf, конвертация описана в конце.

## Разметка внутри шаблона

Два вида вставок в шаблоне и третий в рабочем документе, все машинно проверяемы.

В `{{ЗАГЛУШКА_ЗАГЛАВНЫМИ}}` подставляется значение. Найти все незаполненные:

```bash
grep -o '{{[^}]*}}' templates/pmi/pmi-gost-r-59795.md | sort -u
```

Перед сдачей команда должна возвращать пустоту.

Строки, начинающиеся с `>` — пояснения для того, кто пишет документ. В готовый документ они не идут:

```bash
grep -v '^>' PMI-rabochiy.md > PMI-chistovik.md
```

Ещё в файлах есть HTML-комментарии в начале, с описанием разметки. Их тоже вырезают, но конвертеры обычно убирают их сами.

## Статус поля, когда значение известно не до конца

Заглушка говорит «значения нет». На практике между «нет» и «есть» лежит ещё несколько состояний, и их стоит различать в рабочем документе, пока он не ушёл в чистовик. Пометка в квадратных скобках ставится рядом с заглушкой, сама заглушка остаётся:

| Пометка | Когда ставится |
| --- | --- |
| `[ПОДТВЕРЖДЕНО]` | Есть прямой источник: пункт ТЗ, номер ответа, страница документа |
| `[ЧАСТИЧНО]` | Подтверждена часть сведений, остальное в реестре уточнений |
| `[ПРОТИВОРЕЧИЕ]` | Два источника расходятся. Оба сохраняются со ссылками, значение не выбирается без правила приоритета |
| `[ТРЕБУЕТ ДАННЫХ ЗАКАЗЧИКА]` | Поле зависит от внедрения: площадка, роли, пороги, сроки хранения |
| `[ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ ПОСТАВЩИКА]` | Нужен юридически или технически авторитетный источник: версия, сертификат, гарантия |
| `[НЕПРИМЕНИМО: обоснование]` | Поле исключено по зафиксированной причине. Без обоснования исключать нельзя |

Пометки ищутся грепом:

```bash
grep -o '\[[А-ЯЁ][^]]*\]' work/PMI-mysystem-v0.1.md | sort | uniq -c
```

В чистовик ни одна пометка не идёт. `[ПОДТВЕРЖДЕНО]` просто снимается, остальные превращаются в значения или в строки реестра уточнений, а `[НЕПРИМЕНИМО: ...]` становится абзацем с обоснованием в тексте раздела.

Раздел «Метрологическое обеспечение» для программной системы хочется удалить. Стандарт разрешает исключать разделы только с переносом содержания, поэтому на месте раздела остаётся абзац с обоснованием.

## Порядок работы

Скопируйте шаблон под рабочим именем с версией: `PMI-<система>-v0.1.md`. Правьте копию, шаблон в репозитории не трогайте.

Соберите исходные данные до того, как начнёте писать. Что откуда берётся, описано в data-sources.md. Заполнять шаблон по памяти, «уточню потом», не выйдет: половина полей ссылается на пункты ТЗ, и без ТЗ под рукой вы напишете то, что придётся переписывать.

Заполняйте сверху вниз, но перечень проверок делайте после матрицы соответствия из приложения В. Так проще: сначала выписываете требования ТЗ, попадающие в объём испытаний, потом на каждое заводите проверку. Обратный порядок даёт проверки без требований и требования без проверок.

Дальше методики. Одна проверка, одна методика, с теми же идентификаторами.

Параллельно с первым черновиком заводится реестр уточнений по форме templates/pmi/clarifications-register.md. Каждая заглушка, которую нельзя закрыть без другой стороны, становится строкой реестра с ответственным и сроком. Параметры стенда уходят в лист готовности по форме templates/pmi/stand-readiness-sheet.md, в ПМИ на него только ссылка. Обе формы собраны под серверную систему с несколькими сторонами; для небольшого продукта реестр ведётся одной таблицей без сводок, а лист сжимается до среды выполнения, поставки и готовности людей.

Потом чек-лист: templates/pmi/release-checklist.md, целиком, а не по памяти.

## Версии

Версия отражается в трёх местах сразу: имя файла, титульный лист, лист регистрации изменений. По имени файла коллега отличает актуальную редакцию от вчерашней, по титулу это видит заказчик, по листу изменений рецензент понимает, что именно поменялось после его замечаний.

В листе изменений пишутся факты: какие пункты переписаны, какие проверки добавлены. Заглушки вида «перечень изменённых пунктов заполняется при выпуске» из выпущенного документа удаляются, он уходит на широкий круг читателей.

## Ссылки на пункты ТЗ

Каждая проверка ссылается на пункт ТЗ. Перед сдачей ссылки проверяются по живому ТЗ: открыли пункт, увидели требование, сверили формулировку. Не «должно совпадать», а увидели.

Числа переносятся дословно. Если в ТЗ написано «не менее ~105 транзакций в секунду», в ПМИ идёт та же формулировка со знаком приблизительности. Округление в свою пользу вскрывается на приёмке, и дальше обсуждается уже не производительность, а доверие к документу.

## Конвертация в .docx

Прямой путь через pandoc:

```bash
grep -v '^>' PMI-rabochiy.md > /tmp/pmi-clean.md
pandoc /tmp/pmi-clean.md -o PMI-<система>-v1.0.docx --reference-doc=шаблон-организации.docx
```

`--reference-doc` подставляет стили, нумерацию и колонтитулы вашей организации. Без него получится документ со стилями pandoc по умолчанию, который нормоконтроль вернёт.

Что проверить после конвертации:

1. открыть в настоящем Microsoft Word, не только в LibreOffice: расхождения по нумерации и полям видны именно там;
2. пересобрать оглавление и убедиться, что нет битых ссылок;
3. проверить, что таблицы не разъехались по ширине страницы;
4. убедиться, что в файле не осталось режима записи исправлений и примечаний от черновика.

Оформление текстовых документов задаёт ГОСТ Р 2.105-2019. Если в организации есть свой шаблон .docx, он уже учитывает эти требования, и брать надо его.

## Что не делать

Не смешивайте в одном файле шаблон и рабочий документ. Через две недели вы не вспомните, где были пояснения, а где ваш текст.

Не удаляйте разделы, которые «не про нас». ГОСТ Р 59795-2021 разрешает объединять и исключать разделы, но только при условии, что содержание изложено в других разделах. Раздел про метрологическое обеспечение чаще всего не удаляют, а заполняют одним абзацем с обоснованием.

Не заполняйте таблицы наполовину, оставляя прочерки «пока так». Прочерк в готовом документе читается как «мы не знаем», и рецензент задаст вопрос именно по этой строке.
