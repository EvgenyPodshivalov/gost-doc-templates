# Приложение А к ПМИ. Тесты (контрольные примеры)

Тесты входят в ПМИ приложением, это прямое требование ГОСТ Р 59792-2021 п. 3.7. Отдельным документом их выпускать не нужно, если только заказчик не потребовал этого в ТЗ.

## Что должен обеспечивать тест

Требования разные для автономных и комплексных испытаний, и путать их не стоит.

Тесты на этапе автономных испытаний (п. 4.2.3):

1. полную проверку выполнения функций и процедур по перечню, согласованному с заказчиком;
2. необходимую точность вычислений, установленную в ТЗ;
3. проверку основных временных характеристик функционирования программных средств, если это требуется;
4. проверку показателей составных частей системы на соответствие требованиям ТЗ.

Комплексный тест (п. 4.3.5):

1. проверку выполнения функций во всех режимах функционирования, установленных в ТЗ, включая взаимодействие между частями системы;
2. проверку реакции системы на некорректную информацию и аварийные ситуации;
3. проверку показателей системы в целом и её составных частей на соответствие требованиям ТЗ.

Второй пункт комплексного теста забывают чаще остальных. Сценарии с мусорными данными и аварийным завершением пишутся заранее, наравне с основными.

## Исходные данные

ГОСТ Р 59792-2021 п. 4.2.4 рекомендует брать фрагмент реальной информации заказчика в объёме, достаточном для достоверности испытаний. На практике это упирается в режим доступа: реальные данные почти всегда содержат сведения ограниченного доступа. Три рабочих варианта, по убыванию убедительности для приёмочной комиссии:

- обезличенный срез боевых данных, подготовленный заказчиком;
- синтетические данные, повторяющие структуру и объём боевых;
- демонстрационный набор из поставки.

Выбор фиксируется в ПМИ до испытаний. Если решили брать срез боевых, заранее согласуйте обезличивание со службой безопасности заказчика: это дольше, чем кажется.

## Форма контрольного примера

| Поле | Содержание |
| --- | --- |
| Идентификатор | Т-01 |
| Связанная проверка | П-01 |
| Пункт ТЗ | {{ПУНКТ_ТЗ}} |
| Наименование | {{НАИМЕНОВАНИЕ_ТЕСТА}} |
| Предусловия | {{ПРЕДУСЛОВИЯ}} |
| Входные данные | {{ВХОДНЫЕ_ДАННЫЕ}} |
| Шаги | {{ШАГИ}} |
| Ожидаемый результат | {{ОЖИДАЕМЫЙ_РЕЗУЛЬТАТ}} |
| Артефакт-доказательство | {{АРТЕФАКТ}} |
| Согласован с заказчиком | {{ДА_НЕТ_РЕКВИЗИТЫ}} |

Строка «Артефакт-доказательство» нужна, чтобы после прогона не спорить, чем подтверждается результат. Снимок экрана, выгрузка журнала за интервал, ответ сервиса, отчёт нагрузочного инструмента. Записывается до испытаний.

Строка про согласование с заказчиком тоже не формальность. Перечень функций и процедур для автономных тестов согласовывается по п. 4.2.3, а комплексные тесты по п. 4.3.3 должны быть согласованы к моменту предъявления системы на комплексные испытания.

## Пример заполнения

Пример условный, все значения вымышлены. Он показывает степень детализации, а не содержание вашей системы.

| Поле | Содержание |
| --- | --- |
| Идентификатор | Т-07 |
| Связанная проверка | П-07 |
| Пункт ТЗ | 4.2.3 |
| Наименование | Отказ в обработке файла с неподдерживаемой кодировкой |
| Предусловия | Испытатель авторизован под ролью «Оператор», очередь загрузки пуста |
| Входные данные | Файл `sample-cp1251.csv`, 120 строк, кодировка windows-1251, декларированная кодировка UTF-8 |
| Шаги | 1. Загрузить файл через форму импорта. 2. Дождаться завершения обработки. 3. Открыть журнал обработки за текущие сутки |
| Ожидаемый результат | Файл отклонён, оператор видит сообщение с кодом ошибки и указанием строки, в журнале запись уровня ERROR, ранее загруженные записи не изменены |
| Артефакт-доказательство | Снимок экрана с сообщением, выгрузка журнала за интервал прогона |
| Согласован с заказчиком | Да, протокол согласования от {{ДАТА}} |

## Типовые ошибки в приложении А

Тест дублирует методику из раздела 8 слово в слово. Тогда одно из двух лишнее: методика описывает порядок проверки, тест даёт конкретные данные и ожидаемые значения.

Ожидаемый результат написан как «система работает корректно». Проверить это нельзя, значит на приёмке результат будет определяться на глаз, а спор выиграет тот, кто громче.

Тестов меньше, чем проверок. Каждая функциональная проверка нуждается хотя бы в одном контрольном примере, документарные проверки комплектности и качества документации обходятся без них.

Данные привязаны к конкретному стенду: адреса, идентификаторы записей, имена узлов. При переносе испытаний на площадку заказчика такой тест приходится переписывать целиком.
